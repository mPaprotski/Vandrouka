# День 28 — интеграция игрового цикла

Программная часть завершена 20 октября 2026 года. **День 28 целиком ещё не закрыт:**
пользователь сообщил, что сценарий на физическом телефоне пока не тестировал.
Android E2E и полевые GPS/камера/разрешения остаются критериями приёмки.

## Найдено и исправлено

1. Старый экран мог вызвать общий session controller уже после входа другого
   пользователя и выполнить действие с его токеном. В `withAccess` добавлен
   `expectedOwner`; камера, upload, confirm и очистка черновика закреплены за владельцем
   экрана. Несовпадение отменяет запрос до вызова операции. Смена сессии во время
   запроса дополнительно защищена существующим epoch. Регрессионный тест воспроизвёл
   проблему до исправления и проходит после него.
2. Запоздалая очистка черновика могла удалить фото, уже подтверждённое другим
   контроллером. Клиент теперь вызывает `discardPhoto`, а не обычный delete.
   `DELETE /v1/visits/photos/{photo_id}?unconfirmed_only=true` блокирует строку фото,
   затем проверяет confirmed visits в новом SQL statement snapshot. Если подтверждение
   уже есть — `409 photo_confirmed`, без tombstone, deletion job и обращения к S3.
   Обычный DELETE остаётся явным удалением владельцем и сохраняет XP/защиту награды.
3. Фоновая TTL-очистка имела проверку NOT EXISTS и изменение в одном CTE snapshot.
   Она могла не увидеть посещение, закоммиченное между чтением и получением блокировки.
   Теперь выбор/блокировка кандидатов и проверяемый UPDATE — отдельные statements
   одной транзакции. После блокировки используется свежий снимок; новая confirmation
   не может вклиниться до коммита, поскольку ей нужна та же блокировка фото.

Миграций и новых endpoint нет; добавлен необязательный query parameter к DELETE.
OpenAPI обновлён. GPS-пороги, +100 XP, уровни и правила удаления истории не менялись.

## Воспроизводимая локальная интеграция

Добавлен `scripts/verify_game_loop.mjs` и небольшой синтетический JPEG fixture.
Запуск из корня репозитория с Node 22:

```bash
node --experimental-strip-types scripts/verify_game_loop.mjs
```

Перед запуском должны работать Compose API/PostgreSQL/MinIO с актуальным кодом:

```bash
docker compose --env-file backend/.env up -d --build api
```

`TEST_API_URL` по умолчанию `http://127.0.0.1:8080`; разрешён только HTTP loopback origin.
Скрипт запрещает redirects и запросы на другой origin, не открывает карту/маршруты
и не вызывает Mapbox. Docker Compose нужен для проверки XP и очистки только
автоматически созданных тестовых аккаунтов. До изменения sessions проверяется,
что API и Compose видят того же пользователя по сгенерированному email/ID.
Не использовать для физического телефона: fixture и GPS в этом тесте искусственные.

Проверено на реально запущенных локальных API/PostgreSQL/MinIO:

| Сценарий | Результат |
|---|---|
| JPEG multipart upload, confirm, искусственная потеря ответа после коммита | Сохранённая неопределённая попытка |
| Новый session/photo controller, чтение сохранённого журнала | Прежний key/body, replay +100 XP |
| Новое фото и посещение того же места | 0 XP |
| GPS вдали → отказ → свежий GPS и новый ключ | rejected, затем confirmed 0 XP |
| Access принудительно истёк только у тестового пользователя | Refresh и успешный повтор |
| Pending первого аккаунта, logout и вход вторым | Чужой pending не показывается, старый экран не отправляет запрос |
| Чтение/очистка чужого фото | 404 |
| Первое посещение вторым аккаунтом | Свои +100 XP |
| Возврат в первый аккаунт и replay его pending | 0 XP, без повторной награды |
| Защищённая очистка confirmed фото | 409, фото остаётся доступным владельцу |

В БД у первого тестового аккаунта 5 visits и одна награда 100 XP, у второго —
1 visit и одна награда 100 XP. Скрипт завершился PASS; фото/аккаунты очищены в finally.
Удаление metadata может повторно поставить ключ уже удалённого объекта в штатную
очередь очистки; worker обрабатывает такие удаления идемпотентно.

В этой интеграции используются реальные API client, session/photo controllers и
journal implementation. Native camera, GPS, SecureStore и FormData file URI bridge
заменены адаптерами. Это проверка связности и отказоустойчивости, **не Android E2E**.

## Осталось проверить на CMF Phone 2

Запись результата: **не тестировалось**, со слов пользователя 20 октября.

1. Перезапустить Expo Go/Metro после новых зависимостей. Убедиться, что телефон
   открывает Metro `/status` и API `/health` по текущему LAN IP ноутбука.
   При смене Wi-Fi/режима модема обновить `EXPO_PUBLIC_API_URL` и адрес Metro;
   VPN-адрес tun0 не использовать для LAN.
2. Войти → открыть место из **списка** (без загрузки Mapbox) → снять фото.
   Проверить разрешение камеры, ориентацию, предпросмотр, пересъёмку и отмену.
3. У места, в радиусе 50 м и с GPS accuracy ≤30 м: загрузить и подтвердить.
   За первое место ожидается +100 XP; после нового фото того же места — 0 XP.
4. Проверить отказ в GPS/камере, выключенную геолокацию, неточную фиксацию,
   разрешение через настройки и возврат из фона. Ошибка не должна ломать приложение.
5. Выключить сеть/свернуть при подтверждении, вернуть сеть, проверить результат.
   При неизвестном исходе закрыть Expo Go и открыть то же место снова:
   восстанавливается прежняя попытка. Двойного XP нет.
6. Выйти и войти вторым аккаунтом: pending/результат/фото первого недоступны.
   Вернуться в первый и завершить его pending.
7. Записать по каждому пункту PASS/FAIL и шаг ошибки. Не отмечать полевую проверку
   пройденной по одному успешному открытию приложения.
