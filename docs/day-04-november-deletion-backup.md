# 4 ноября — удаление и резервные копии

## Пользовательское удаление

В истории добавлены «Удалить фото» и «Удалить из истории» с явным подтверждением.
Первое использует существующий DELETE photo; визит и XP сохраняются.
Второе вызывает DELETE /v1/users/me/visits/{id}: скрывает подтверждённый визит,
помечает фото удалённым, ставит файл в durable queue. Повтор DELETE возвращает 204.
Чужая/несуществующая запись — 404. XP ledger и запись идемпотентности сохраняются:
новое посещение не выдаёт ещё +100 XP. После скрытия последнего видимого визита
место исчезает из личной карты (она строится по видимой истории), но XP остаётся.

В профиле добавлено окончательное удаление аккаунта с текущим паролем:
DELETE /v1/me {password}. Владелец определяется Bearer, не телом запроса.
Удаляются аккаунт, visits, photos metadata, XP, все session families/sessions.
Чужой аккаунт выбрать нельзя; неправильный пароль — 403 без удаления.
До 5 попыток/минуту/owner, до 2 одновременных проверок пароля на процесс.
После ответа клиент выполняет logout и очищает сессию. При неизвестном исходе
не показывает ложный успех; можно выйти и проверить повторный вход.
После подтверждённого удаления очищаются зашифрованные pending-confirm записи
из owner-индекса. Индекс сохраняется до самой записи журнала; deleted-marker
не позволяет позднему callback снова записать GPS. Очистка не затрагивает другой
origin/owner. Отложенный logout также закреплён за удаляемым owner и не завершит
вход нового аккаунта. Для старых неиндексированных записей дополнительно
проверяются ID текущего каталога; при чтении старый журнал мигрирует в индекс.
Legacy-записи мест, уже отсутствующих в каталоге и ни разу не прочитанных после
обновления, перечислить через SecureStore невозможно; их полное удаление не
гарантируется. При недоступном SecureStore серверное удаление не отменяется,
пользователь получает уведомление о неполной локальной очистке. При потере
ответа DELETE успех не заявляется; автоматическая локальная очистка в таком
неопределённом состоянии не выполняется.

Фото немедленно недоступно для новых API-чтений. Физическое удаление файлов
асинхронное: queue переживает удаление аккаунта и недоступность S3.
При удалении аккаунта очередь ждёт окончания upload lease, чтобы поздняя запись
не создала осиротевший файл. При остановленном API/Free Render cleanup не работает;
выполнится после запуска. Уже выданные байты фото невозможно отозвать с устройства.

## Backup и безопасная репетиция

Из корня проекта:

```bash
python3 scripts/backup_local.py /absolute/private/path/new-backup
python3 scripts/verify_backup.py /absolute/private/path/new-backup
```

Первый скрипт кратко останавливает только API, делает pg_dump -Fc и архив
MinIO volume read-only без сети, пишет SHA-256 manifest. API возобновляется в finally.
Если API изначально остановлен, скрипт не запускает его. Папка должна быть новой
и вне Git-репозитория; права 0700. Это приватный архив, содержащий email,
password hashes, session hashes и файлы. Не публиковать/не прикладывать в чат.
Нельзя параллельно запускать импортеры, административные SQL-записи или другой API.
Снимок согласован только при отсутствии иных писателей.

Второй скрипт проверяет SHA-256, восстанавливает dump в уникальную disposable DB,
архив — во временную директорию; проверяет пути/типы архивных записей, не допускает
симлинки. Проверочные данные удаляются в finally; рабочие БД и volume не изменяются.
Не поднимает S3-сервер на распакованном volume и не доказывает HTTP-чтение
восстановленных фото. Восстановление в production скриптом намеренно не реализовано.
После аварийного production restore необходимо отозвать восстановленные сессии
и повторно применить удаления после момента snapshot, иначе удалённые аккаунты/фото
могут вернуться из старого архива.

## Эксплуатационные ограничения

Скрипты предназначены для локального Compose, не Neon/R2. Для внешнего окружения
нужны отдельные PostgreSQL dump и S3-copy с согласованной остановкой записей,
второе независимое место хранения, шифрование и расписание с проверкой статуса.
Не настраиваем расписание на ноутбуке без выбранного постоянного хранилища.
Рекомендуемая первоначальная политика: ежедневная копия, хранение 7 дней,
удаление просроченных копий и учёт удалений при восстановлении; фактически
автоматическое расписание и внешняя копия пока не настроены.

При продолжении MinIO успешно выполнил диагностические PUT/DELETE и полный
игровой E2E; свободного места стало около 2,9 ГБ. Причина прежнего 503 однозначно
не установлена. Защитные пороги MinIO не отключались, пользовательские volumes
не удалялись; малый запас места требует наблюдения.
Mapbox не вызывался. Удаление на физическом телефоне ещё требуется проверить
на отдельном тестовом аккаунте, включая потерю ответа и последующий вход.
