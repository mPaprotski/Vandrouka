# День 27 — подтверждение посещения из Expo Go

Код реализован 20 октября 2026 года, досрочно. Локальный сквозной сценарий
прошёл. Полный сценарий на физическом телефоне пока не подтверждён: это
остаётся открытой проверкой дней 26–28.

## Пользовательский сценарий

Вход → карточка места → **Сделать фото места** → снимок → **Загрузить фото** →
**Подтвердить посещение** → новый foreground GPS → результат сервера.

Показываются **«Место открыто — +100 XP»**, **«Повторное посещение — 0 XP»**
или причина отказа: подойти ближе, улучшить accuracy, обновить GPS/время,
дождаться готовности фото, недоступное место. Суммарный баланс/уровень и
экран истории не добавлялись — здесь только результат конкретного посещения.

Клиент использует существующий `POST /v1/places/{id}/visits` с Bearer и UUID
`Idempotency-Key`. GPS, полученный до upload, не используется для нового confirm:
перед ним получается свежая фиксация с известной accuracy ≤30 м. Пороги окончательно
проверяет backend (50 м / 30 м / 120 с / +30 с). Mapbox не требуется.

HTTP 201/200 декодируются как confirmed, 422 как сохранённый rejected; проверяются
place/photo, статус, timestamps и согласованность XP/error. Несогласованный ответ
не считается успехом. В запрос не попадают client user/status/XP.

## Повтор, хранение и очистка

Перед первой отправкой создаётся UUID и записывается полный нормализованный запрос.
SecureStore содержит одну незавершённую попытку на пару backend origin / owner / place:
UUID, готовое фото (только публичные metadata), photo ID и GPS-тело запроса.
Ключ содержит SHA-256 origin и числовые owner/place; запись дополнительно проверяет
эти значения и version. Пароли/токены, local file URI и EXIF туда не включаются.
GPS хранится зашифрованно, только пока требуется воспроизвести неопределённый исход.
В логи и URL он не попадает. Нет web/plain-text fallback и фоновой отправки.

- Пока идёт GPS/подтверждение, второй запрос из UI не запускается.
- Ошибка записи SecureStore не позволяет отправить запрос. Повтор сначала
  повторяет сохранение; существующая попытка не заменяется новым UUID/фиксацией.
- Таймаут, потерянный ответ, отмена отправки, сетевые/серверные ошибки и неверный
  ответ сохраняют попытку. **Проверить результат** отправляет то же тело/ключ,
  без нового GPS. Сервер возвращает исходный результат, даже если GPS уже устарел.
- Закрытие/фон прерывают watcher/запрос и не дают позднему ответу восстановить UI.
  После входа тем же пользователем и открытия камеры того же места незавершённая
  попытка восстанавливается. Другой аккаунт/сервер/место не получает её данные.
- После confirmed/rejected журнал очищается с проверкой ожидаемого UUID. Если
  очистка не удалась, запрос остаётся доступен для безопасного replay.
  Операции с одним ключом хранилища сериализованы; старый экран не может стереть
  новую попытку или перезаписать отличающееся тело.
- После сохранённого rejected разрешены новый GPS/UUID с тем же готовым фото либо
  пересъёмка. При known rejected фото не было использовано подтверждением.
- Подтверждённое фото и фото с неопределённым исходом защищены от удаления обычной
  очисткой черновика. Это исправляет поведение дня 26, где закрытие удаляло upload.
- Domain `404 not_found` и `409 photo_already_used` приходят в текущем backend после
  поиска idempotency outcome. Для такого ключа сохранённого результата нет, фото
  непригодно для этой попытки: журнал очищается и предлагается пересъёмка. Само
  удалённое/уже использованное фото клиент не удаляет. Generic/proxy 404 без этого
  кода, 500 и `idempotency_conflict` не считаются доказательством завершения.
- Повреждённый/недоступный журнал блокирует новую попытку до успешного чтения,
  без молчаливого удаления данных. Автоматического восстановления повреждённых
  записей и account deletion UI в этом этапе нет.

Незавершённый запрос не отправляется автоматически после restart. При неизвестном
исходе сервер мог уже начислить XP; отмена запроса не является отменой посещения.
Подтверждённые фото сохраняются сервером, локальный cache-снимок удаляется при уходе.

Для UUID и SHA-256 через `expo install` установлен `expo-crypto ~57.0.4`,
[включённый в Expo Go SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/crypto/).
Используется существующий SecureStore без biometric prompt, с
`WHEN_UNLOCKED_THIS_DEVICE_ONLY`. Нативные проекты и эмулятор не создавались.

## Проверки

- Unit-тесты контроллера: свежий GPS, +100/0, запись до отправки, отказ и новая
  попытка, двойное нажатие, late response, отмена, повтор после restart, GPS/storage
  errors, очистка после успеха, защита медиа, изоляция и конкурентный доступ к журналу.
- API-тесты: точные header/body, 201/200/422, неверный key, конфликт, несогласованные
  status/XP/place/photo и сохранение HTTP Request ID в ошибке.
- Реальные mobile API/session/photo controllers + локальные API/PostgreSQL/MinIO:
  JPEG upload → confirm с реальным коммитом и искусственно потерянным ответом →
  новый controller с восстановленным журналом → replay того же ключа → +100;
  второе фото/visit → 0; GPS too_far → 422 → новый ключ и корректный GPS → 0.
  В БД проверены 4 посещения (3 confirmed, 1 rejected) и одна награда 100 XP.
  После закрытия контроллеров confirmed фото читается владельцем и не удаляется.
  Временные аккаунт/фото удалены после smoke.
  Native camera/GPS/SecureStore и RN file URI transport в этом smoke заменены
  фиксированными адаптерами; это не доказательство работы Android bridge.

## Физическая проверка

1. Перезапустить Metro после установки новой зависимости: `cd mobile && npm start -- --clear`.
   API и MinIO должны работать, LAN API URL в `.env.local` должен быть доступен телефону.
2. В Expo Go войти и открыть место из **списка**, чтобы не загружать Mapbox-карту.
3. Рядом с реальным местом (≤50 м) сделать фото, загрузить, подтвердить с точным GPS.
   Ожидается +100 XP; для уже награждённого места — 0 XP.
4. Уйти со страницы результата. Вернуться, сделать новое фото того же места:
   подтверждение должно дать 0 XP. Старое confirmed фото должно остаться на сервере.
5. Проверить отказ вдали от места и новый успешный запрос после подхода с тем же фото.
6. Оборвать сеть/свернуть во время отправки, вернуть сеть и нажать **Проверить результат**.
   Не должно быть второй первой награды. Если запрос не дошёл, возможен сохранённый
   отказ по устаревшему GPS; после него разрешена новая попытка.
7. При неизвестном исходе перезапустить Expo Go и открыть камеру того же места:
   должна появиться проверка прежней попытки, а не новая камера.
8. Выйти/войти другим аккаунтом: чужой pending/result/фото не показываются.
