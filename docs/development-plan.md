## 1. Продукт и результат релиза

**Миссия:** сделать культурное наследие частью повседневной жизни человека.
**Идея:** превратить реальный город в игровую карту, которую хочется исследовать.

Основной цикл MVP:

**Карта → объект → прогулка → GPS + фото → подтверждённое посещение →
+100 XP и уровень → история и личная карта → следующее открытие.**

Первый город — Минск. Первый клиент — Android на Expo + React Native +
TypeScript. Обязательное требование: запуск в Expo Go на физическом телефоне.
Эмулятор на компьютере не запускаем. Серверная маршрутизация остаётся Mapbox.
Отображение карты — Mapbox GL JS через react-native-webview (решение пользователя).
WebView входит в Expo Go SDK 57; работу WebGL, жестов, маркеров и обмена
сообщениями с React Native нужно проверить на физическом телефоне.
Нативный Mapbox SDK не используем. Flutter в план не входит.

Planner помогает добраться до объектов, но игровой цикл работает и без
генерации сложного маршрута. Реальные партнёрские награды — важное направление
продукта после MVP, а не обязательство релиза 15 ноября.

## 4. Архитектура и правила, которые нельзя потерять

### Модули

Сохраняем один Go backend и PostgreSQL. Добавляем auth, users, visits, media,
progress; achievements/collections — только P1. Микросервисы не выделяем.

Мобильное приложение располагается в `mobile/` внутри репозитория. Навигация
строится вокруг Map, PlaceDetails, Profile и Visits; login/register и камера —
части соответствующих пользовательских сценариев. Приватные экраны требуют сессии.
API URL задаётся окружением; для телефона используется доступный адрес backend.

Существующий `GET /v1/cities/{slug}/places` сохраняется. Новый дублирующий каталог
не нужен. Контракты новых API добавляются в существующий OpenAPI до интеграции UI.

### Данные и согласованность

- Users и sessions/refresh sessions; пароль хранится как стойкий хэш.
- Visits: владелец, place, статус, серверное время и необходимые данные проверки.
- Visit photos: владелец, приватный ключ файла, формат/размер, связь с посещением.
- XP transactions: событие посещения, величина награды; уникальная связь с наградой.
- Источник истины — подтверждённые посещения и журнал XP, а не клиентский баланс.
- Первое подтверждённое посещение user/place даёт +100 XP; повторы не дают XP.
- Подтверждение посещения и начисление XP выполняются в одной транзакции.
- Идемпотентный повтор возвращает уже полученный результат; параллельные запросы
  не создают вторую награду. Ограничения БД дополняют проверки приложения.
- Upload выполняется до подтверждения; проверяется владелец, готовность файла
  и соответствие правилам. Для незавершённых upload предусмотрена очистка.

Не откладываем транзакционную модель XP до отдельного позднего этапа: она
проектируется вместе с visits и входит в первый работающий игровой цикл.

### Подтверждение и приватность

Сервер проверяет аутентификацию, активность места, расстояние, accuracy,
свежесть/корректность timestamp, принадлежность фото и ограничения повторов.
Клиент не выбирает награду, уровень или итоговый статус. Радиус, допустимая
точность и свежесть — серверные настройки; стартовые значения фиксируются
перед реализацией GPS-проверки и затем проверяются на устройстве и в поле.
GPS и фото не считаются абсолютным доказательством присутствия; ML в MVP нет.

Фото и история приватны. Контролируем MIME, фактический формат и размер;
удаляем ненужные метаданные фото, не публикуем постоянные открытые ссылки.
Минимизируем хранение координат, не пишем их в обычные логи. Удаление своей
истории/фото и аккаунта предусматриваем до релиза с описанным поведением XP.
Тесты доступа к чужим объектам обязательны. Фонового трекинга нет.

Локально используем приватное S3-совместимое фотохранилище (например MinIO),
демо — совместимое приватное хранилище с постоянным томом/бакетом. Конкретное
место развёртывания и доступы проверяются в первый день; чужие контейнеры
или бакеты из других проектов не переиспользуем без отдельного решения.
Redis не является зависимостью MVP: текущие лимиты подходят одному экземпляру
API. Несколько экземпляров потребуют отдельного решения об общих счётчиках.

## 6. Минимальный API нового сценария

Добавляем в OpenAPI и реализуем по этапам; точные DTO фиксируются перед кодом.

| Группа | Минимальные операции |
|---|---|
| Auth | POST /v1/auth/register, /login, /refresh, /logout |
| Профиль | GET /v1/users/me; операция удаления своего аккаунта |
| Медиа | POST /v1/visits/photo-upload; приватное чтение/удаление своего фото |
| Посещение | POST /v1/places/{id}/visits; идемпотентность, один первый XP на user/place |
| История | GET /v1/users/me/visits; приватное получение/удаление своей записи |
| Прогресс | GET /v1/users/me/progress |
| P1 | Каталог/свои achievements; одна collection — только если допущены |

Конкретные правила удаления и их влияние на XP согласовать до реализации:
удаление фото не должно случайно стирать награду, а удаление/повторная отправка
истории не должны позволять повторно получать XP. Это отдельная продуктовая
проверка 22–23 октября, не повод выдавать несогласованное поведение за готовое.
Дополнительный /users/me/map не обязателен: клиент может объединять каталог
с историей посещений. Не принимаем client user_id как основание доступа.

## 7. Контент и проверка качества

Используем существующие 60 мест без расширения географии до релиза. На 20 октября
нужны проверенные 5–10 компактных точек для E2E и поля. Остальной каталог не
блокирует этот маршрут, но не должен содержать заведомо опасные/закрытые подходы
или недоказанные обещания доступности. Обложки опциональны, состояния без фото
обязательны. Неизвестные цены/часы не выдаются за бесплатный вход/круглосуточность.
Внешний каталог остаётся вне Git; тестовые фикстуры и правила воспроизводимости
остаются в репозитории. Медиа пользователей хранятся отдельно от справочников.

## 8. Ежедневные проверки и Definition of Done

Для backend-изменений: содержательные unit/integration tests, race, vet, build,
форматирование, OpenAPI. PostgreSQL-интеграции должны действительно запускаться
в CI; пропуск тестов из-за окружения отмечается явно. Для новых транзакций —
rollback, повторы и параллельные запросы. Для mobile — typecheck/lint, тесты
критической логики и Android smoke. Версии нативных зависимостей фиксируются
lockfile и проверенной dev/release сборкой, а не только запуском bundler.
Mapbox-квота расходуется только осознанными сквозными проверками.

К 15 ноября:

- [ ] APK устанавливается на чистый Android и работает без Metro.
- [ ] Есть карта Минска, реальные места и карточка; отказ в GPS/камере обработан.
- [ ] Регистрация/вход/refresh/logout и восстановление сессии работают.
- [ ] Фото снимается в приложении, приватно загружается и связано с посещением.
- [ ] Сервер отклоняет неверные координаты/accuracy/time и чужие файлы.
- [ ] Первое подтверждение и +100 XP атомарны; повтор/конкуренция не дают второй XP.
- [ ] Уровень и XP берутся с сервера; профиль/история/маркеры согласованы после restart.
- [ ] История и фото защищены по владельцу; сценарии удаления определены и проверены.
- [ ] Пройдены Android E2E и полевой сценарий на целевой сборке.
- [ ] Старые каталог/generate/recalculate не сломаны.
- [ ] CI, миграции, backup/restore и полный Docker build проверены.
- [ ] Демо-backend и приватное фотохранилище доступны с телефона.
- [ ] Переданы APK, README, API/схема, демо-сценарий и известные ограничения.

Достижения, коллекции и партнёрские награды не включаются в этот DoD как P0.
Зелёные тесты не заменяют полевую проверку, а готовая документация — приложение.

## 9. Сокращение объёма и блокеры

| Если | Действие |
|---|---|
| К 18–20 октября карта/dev build не работают | Сначала устранить нативный блокер; не переходить на другой стек без обсуждения |
| К 22 октября auth не готов | Оставить один email/password способ; OAuth/reset password не добавлять |
| К 28 октября нет Android E2E посещения | Все P1-дни превратить в резерв основного цикла |
| К 2 ноября история/личная карта не готовы | Упростить визуализацию до списка и двух типов маркеров, сохранить серверный прогресс |
| К 7 ноября есть P0-блокеры | Не начинать достижения, коллекции и мобильный planner |
| GPS нестабилен | Диагностика accuracy и повторная проверка; пороги не ослаблять вслепую |
| Срывается срок P0 | Немедленно обсудить объём/срок с пользователем; не маскировать незавершённость галочкой |

Не сокращаем защиту чужих данных, атомарность XP, сохранение истории, реальную
Android-сборку и полевую проверку. Любое изменение дедлайна, стека, города или
перенос партнёрских наград в MVP требует отдельного решения пользователя.
Рутинные детали реализации выбираются в рамках этих границ. Новые спорные
продуктовые правила уточняются до их реализации.

## 10. После MVP

Отдельный backlog: полноценные коллекции/квесты, достижения и районы/города,
планирование по непосещённым местам, дневник маршрутов, партнёрский пилот и
реальные награды, затем социальные/образовательные сценарии и новые города.
У реальных наград отдельные задачи: партнёры и условия, право на награду,
выдача/погашение кодов, защита от повторов, финансирование и поддержка.
Наличие концепции не считается реализованной бонусной программой.
