# Планировщик маршрутов

Пакет `backend/internal/planner` отвечает за построение пешеходных маршрутов
по городу. Он полностью изолирован от HTTP, PostgreSQL и конкретного сервиса маршрутизации.
Планировщик принимает список мест (`Place`), параметры запроса (`Request`) и
матрицу времени/расстояний через интерфейс `DistanceMatrix`.

## Модель данных

Модель включает:
- `Point`: географические координаты (широта, долгота);
- `Pace`: темп ходьбы (`slow` — множитель 1.2, `normal` — 1.0, `fast` — 0.85);
- `Schedule` и `Interval`: расписание работы с поддержкой интервалов в минутах от полуночи, разделением дней и исключений по датам;
- `Place`: точка интереса с важностью (1–5), отметкой `MustSee`, длительностью осмотра, расписанием и стоимостью билета в копейках BYN (`TicketCostMinor`);
- `Request`: параметры пользователя (категории, бюджет времени в минутах, точка старта, время начала, темп, опциональный бюджет билетов и seed);
- `Stop`: остановка в маршруте с расчетным временем прибытия и ухода, а также флагами неподтверждённых часов или цены;
- `Metrics`: суммарные показатели маршрута (время ходьбы и осмотра, километры пешком, стоимость билетов в копейках, количество остановок с неподтверждёнными данными, распределение по категориям и итоговая оценка `Score`);
- `Route`: готовый маршрут с упорядоченным списком остановок, метриками и seed.

## Преобразование каталога

Функция `FromCatalogPlace(places.Place) Place`:
- преобразует сущность каталога в доменную модель планировщика;
- переводит подтверждённую цену взрослого билета (или бесплатного) в целое число копеек BYN; при отсутствии подходящей конечной неотрицательной цены BYN отмечает цену как неизвестную;
- парсит интервалы часов работы (`HH:MM-HH:MM`, поддерживается окончание `24:00` как минута 1440);
- учитывает календарные исключения (`opening_exceptions`).

Связывание с Valhalla выполняется через адаптер `RouterMatrixBuilder`,
реализующий интерфейс матрицы `DistanceMatrix`. Индекс 0 соответствует точке
старта пользователя, а индексы `1..N` — местам `places[0..N-1]`.

## Жадный алгоритм (Greedy Planner)

Алгоритм ориентирования с окнами времени строит маршрут последовательно:
1. Маршрут начинается в точке старта `req.Start` в момент `req.StartAt`.
2. На каждом шаге перебираются все доступные непосещённые места-кандидаты:
   - **Ценность**:
     ```text
     value = importance × interest_weight × (1 + must_see_bonus)
     ```
     Для выбранных категорий `interest_weight = 1`, для остальных — `0`.
     При пустом списке категорий учитываются все места (`interest_weight = 1`).
     Для приоритетных мест с `must_see = true` бонус `must_see_bonus = 0.5`.
   - **Достижимость**: проверяется признак `Reachable` в пешеходной матрице между текущей точкой и кандидатом.
   - **Затраты времени**:
     ```text
     deltaTime = walkToPlace + visitTime
     ```
     где `walkToPlace = leg.Seconds / 60 × pace.WalkMultiplier()`.
     Для бюджета и времени остановок используется одна длительность `time.Duration`; ходьба округляется вверх до наносекунды. Если ходьба вместе с осмотром превышает оставшийся бюджет, кандидат отсекается.
   - **Бюджет билетов**: если задан `MaxTicketCostMinor`, суммарная стоимость билетов с учетом кандидата не должна превышать лимит.
   - **Расписание**: вызывается `CanVisit(place, arrival)`. Время прибытия должно гарантировать, что весь интервал осмотра `[arrival, arrival + visitMinutes]` укладывается в один интервал работы.
   - **Эффективность**:
     ```text
     efficiency = value / deltaTime
     ```
3. Выбирается кандидат с максимальной эффективностью `efficiency`.
   В случае одинаковой эффективности кандидатов (с точностью до `1e-9`) выполняется детерминированное разрешение ничьей (tie-breaking) на основе псевдослучайного генератора, инициализированного `req.Seed`.
4. Маршрут заканчивается у последнего посещённого места (возврат к старту не добавляется).

Дубликаты ID обрабатываются по правилу «первая запись определяет место».
Последующие записи с тем же ID игнорируются, даже при отличающихся ценах,
расписании или координатах; используется индекс первой записи в матрице.

Запрос проверяется на положительный бюджет, заданное время, корректные
координаты, темп и неотрицательный лимит билетов. Некорректные места
и достижимые переходы с отрицательными/NaN/бесконечными значениями
возвращают ошибку. Сумма стоимости защищена от переполнения.

## Правила неизвестных данных

- **Часы работы (`hours_known: false`)**: место допускается к посещению (считается открытым), но в остановке выставляется флаг `HoursUnconfirmed = true`.
- **Цены билетов (`price_known: false`)**: в остановке выставляется флаг `PriceUnconfirmed = true`. Для проверки жесткого лимита бюджета билетов такое место считается бесплатным (0 BYN), чтобы не блокировать прогулку, но остановка учитывается в метрике `UnverifiedCount`. Ненулевое значение `TicketCostMinor` при неизвестной цене игнорируется и в итогах. Лимит билетов гарантирует только сумму подтверждённых цен, а фактические расходы при неизвестной цене могут быть выше.
- **Оценка маршрута (Score)**:
  ```text
  score = Σ value - α·walk_km - β·cost_BYN - γ·unverified_count
  ```
  где коэффициенты: $\alpha = 0.5$, $\beta = 0.1$, $\gamma = 0.5$. Неподтверждённые остановки налагают штраф на итоговую оценку.

## Консольная утилита (CLI)

Команда `backend/cmd/planner` позволяет строить маршруты по базе данных Минска через Valhalla:

```bash
cd backend
POSTGRES_DSN='postgres://postgres:postgres@localhost:25432/vandrouka?sslmode=disable' \
VALHALLA_URL='http://localhost:8002' \
go run ./cmd/planner --budget 180 --categories museums,architecture
```

### Параметры запуска
- `--budget` (целое число, по умолчанию `180`): бюджет времени в минутах.
- `--categories` (строка через запятую, по умолчанию `""` — все категории): фильтр категорий (`museums`, `architecture`, `streets`, `monuments`, `parks`, `religious`).
- `--start` (строка `lat,lon`, по умолчанию `53.9032997,27.5561469` — Минская ратуша): стартовая позиция.
- `--start-time` (строка `YYYY-MM-DDTHH:MM` или `HH:MM`, по умолчанию текущее время в поясе `Europe/Minsk`): время начала прогулки.
- `--pace` (`slow`, `normal`, `fast`, по умолчанию `normal`): темп ходьбы.
- `--ticket-budget` (дробное число в BYN, по умолчанию `-1` — не ограничен): предел расходов на билеты.
- `--seed` (целое число, по умолчанию `42`): зерно для воспроизводимости.

## Проверка этапа 19 октября

| Требование | Реализация и проверка |
|---|---|
| Бюджет времени | Одна длительность для допуска и времени остановок; точный лимит, дробное превышение, несколько остановок, разные темпы |
| Расписание | Время после всех предыдущих переходов/осмотров; перерывы, исключения, прибытие на следующую местную дату |
| Билеты | Целые копейки, суммарный лимит, ноль и отсутствие лимита, неизвестные цены и переполнение |
| Повторы | Один ID максимум один раз; первая запись определяет поведение конфликтующих дубликатов |
| Переходы | Направленная матрица от текущей точки; недостижимые места пропускаются |
| Осмотр и показатели | Проверены время осмотра, ходьба, километры, стоимость, отметки неподтверждённых данных и время остановок |
| Воспроизводимость | Повторные запуски с одним seed дают одинаковые остановки и показатели |

Основные проверки находятся в `planner_test.go`, дополнительные регрессии —
в `audit_test.go`. Они используют фиксированные примеры без внешних сервисов.
2-opt, swap, диверсификация, метки и HTTP-эндпоинты не входят в этот этап.

Проверки выполнены 9 октября 2026 года: полный `go test ./... -race -count=1`
с отдельной PostgreSQL-базой `vandrouka_test`, `go vet ./...`, форматирование
и `git diff --check` прошли. Название этапа относится к плановой дате работы.

Сквозной запуск CLI с реальными PostgreSQL и Valhalla:
`--budget 180 --categories museums,architecture --start-time 2026-10-19T10:00 --ticket-budget 15 --seed 42`.
Получены 6 остановок, 59,1 минуты ходьбы, 105 минут осмотра,
164,1 минуты всего, 4,92 км и 0 BYN подтверждённой стоимости.
Все шесть остановок имеют неподтверждённые часы работы. Автоматические
проверки алгоритма не подтверждают фактическую доступность этих мест.
