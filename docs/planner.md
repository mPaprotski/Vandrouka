# Планировщик маршрутов

Текущий провайдер — Mapbox Matrix/Directions API. [Решение и задачи перехода](mapbox-migration.md).

Пакет `backend/internal/planner` отвечает за построение пешеходных маршрутов
по городу. Он полностью изолирован от HTTP, PostgreSQL и конкретного сервиса маршрутизации.
Планировщик принимает список мест (`Place`), параметры запроса (`Request`) и
матрицу времени/расстояний через интерфейс `DistanceMatrix`.

## Модель данных

Модель включает:
- `Point`: географические координаты (широта, долгота);
- `Pace`: темп ходьбы (`slow` — множитель 1.2, `normal` — 1.0, `fast` — 0.85);
- `Schedule` и `Interval`: расписание работы с поддержкой интервалов в минутах от полуночи, разделением дней и исключений по датам;
- `Place`: точка интереса с важностью (1–5), отметкой `MustSee`, длительностью осмотра, расписанием и стоимостью билета в копейках BYN (`TicketCostMinor`);
- `Request`: параметры пользователя (категории, бюджет времени в минутах, точка старта, время начала, темп, опциональный бюджет билетов и seed);
- `Stop`: остановка в маршруте с расчетным временем прибытия и ухода, а также флагами неподтверждённых часов или цены;
- `Metrics`: суммарные показатели маршрута (время ходьбы и осмотра, километры пешком, стоимость билетов в копейках, количество остановок с неподтверждёнными данными, распределение по категориям и итоговая оценка `Score`);
- `Route`: готовый маршрут с упорядоченным списком остановок, метриками и seed.

## Преобразование каталога

Функция `FromCatalogPlace(places.Place) Place`:
- преобразует сущность каталога в доменную модель планировщика;
- переводит подтверждённую цену взрослого билета (или бесплатного) в целое число копеек BYN; при отсутствии подходящей конечной неотрицательной цены BYN отмечает цену как неизвестную;
- парсит интервалы часов работы (`HH:MM-HH:MM`, поддерживается окончание `24:00` как минута 1440);
- учитывает календарные исключения (`opening_exceptions`).

Связывание с Mapbox выполняется через адаптер `RouterMatrixBuilder`,
реализующий интерфейс матрицы `DistanceMatrix`. Индекс 0 соответствует точке
старта пользователя, а индексы `1..N` — местам `places[0..N-1]`.

## Жадный алгоритм (Greedy Planner)

Алгоритм ориентирования с окнами времени строит маршрут последовательно:
1. Маршрут начинается в точке старта `req.Start` в момент `req.StartAt`.
2. На каждом шаге перебираются все доступные непосещённые места-кандидаты:
   - **Ценность**:
     ```text
     value = importance × interest_weight × (1 + must_see_bonus)
     ```
     Для выбранных категорий `interest_weight = 1`, для остальных — `0`.
     При пустом списке категорий учитываются все места (`interest_weight = 1`).
     Для приоритетных мест с `must_see = true` бонус `must_see_bonus = 0.5`.
   - **Достижимость**: проверяется признак `Reachable` в пешеходной матрице между текущей точкой и кандидатом.
   - **Затраты времени**:
     ```text
     deltaTime = walkToPlace + visitTime
     ```
     где `walkToPlace = leg.Seconds / 60 × pace.WalkMultiplier()`.
     Для бюджета и времени остановок используется одна длительность `time.Duration`; ходьба округляется вверх до наносекунды. Если ходьба вместе с осмотром превышает оставшийся бюджет, кандидат отсекается.
   - **Бюджет билетов**: если задан `MaxTicketCostMinor`, суммарная стоимость билетов с учетом кандидата не должна превышать лимит.
   - **Расписание**: вызывается `CanVisit(place, arrival)`. Время прибытия должно гарантировать, что весь интервал осмотра `[arrival, arrival + visitMinutes]` укладывается в один интервал работы.
   - **Эффективность**:
     ```text
     efficiency = value / deltaTime
     ```
3. Выбирается кандидат с максимальной эффективностью `efficiency`.
   В случае одинаковой эффективности кандидатов (с точностью до `1e-9`) выполняется детерминированное разрешение ничьей (tie-breaking) на основе псевдослучайного генератора, инициализированного `req.Seed`.
4. Маршрут заканчивается у последнего посещённого места (возврат к старту не добавляется).

Дубликаты ID обрабатываются по правилу «первая запись определяет место».
Последующие записи с тем же ID игнорируются, даже при отличающихся ценах,
расписании или координатах; используется индекс первой записи в матрице.

Запрос проверяется на положительный бюджет, заданное время, корректные
координаты, темп и неотрицательный лимит билетов. Некорректные места
и достижимые переходы с отрицательными/NaN/бесконечными значениями
возвращают ошибку. Сумма стоимости защищена от переполнения.

## Правила неизвестных данных

- **Часы работы (`hours_known: false`)**: место допускается к посещению (считается открытым), но в остановке выставляется флаг `HoursUnconfirmed = true`.
- **Цены билетов (`price_known: false`)**: в остановке выставляется флаг `PriceUnconfirmed = true`. Для проверки жесткого лимита бюджета билетов такое место считается бесплатным (0 BYN), чтобы не блокировать прогулку, но остановка учитывается в метрике `UnverifiedCount`. Ненулевое значение `TicketCostMinor` при неизвестной цене игнорируется и в итогах. Лимит билетов гарантирует только сумму подтверждённых цен, а фактические расходы при неизвестной цене могут быть выше.
- **Оценка маршрута (Score)**:
  ```text
  score = Σ value - α·walk_km - β·cost_BYN - γ·unverified_count
  ```
  где коэффициенты: $\alpha = 0.5$, $\beta = 0.1$, $\gamma = 0.5$. Неподтверждённые остановки налагают штраф на итоговую оценку.

## Консольная утилита (CLI)

Команда `backend/cmd/planner` позволяет строить маршруты по базе данных Минска через Mapbox:

```bash
cd backend
POSTGRES_DSN='postgres://postgres:postgres@localhost:25432/vandrouka?sslmode=disable' \
go run ./cmd/planner --budget 180 --categories museums,architecture
```

### Параметры запуска
- `--budget` (целое число, по умолчанию `180`): бюджет времени в минутах.
- `--categories` (строка через запятую, по умолчанию `""` — все категории): фильтр категорий (`museums`, `architecture`, `streets`, `monuments`, `parks`, `religious`).
- `--start` (строка `lat,lon`, по умолчанию `53.9032997,27.5561469` — Минская ратуша): стартовая позиция.
- `--start-time` (строка `YYYY-MM-DDTHH:MM` или `HH:MM`, по умолчанию текущее время в поясе `Europe/Minsk`): время начала прогулки.
- `--pace` (`slow`, `normal`, `fast`, по умолчанию `normal`): темп ходьбы.
- `--ticket-budget` (дробное число в BYN, по умолчанию `-1` — не ограничен): предел расходов на билеты.
- `--seed` (целое число, по умолчанию `42`): зерно для воспроизводимости.
- `--optimize` (по умолчанию `true`): оптимизировать порядок через 2-opt и swap; `--optimize=false` оставляет результат greedy.

## Проверка этапа 19 октября

| Требование | Реализация и проверка |
|---|---|
| Бюджет времени | Одна длительность для допуска и времени остановок; точный лимит, дробное превышение, несколько остановок, разные темпы |

## Этап 20 октября: локальная оптимизация

`EvaluateOrder(req, places, matrix, order)` принимает последовательность ID
и полностью пересчитывает переходы, прибытие, уход и показатели. Матрица
остаётся в исходном порядке каталога. Соблюдаются темп, время осмотра,
расписание в часовом поясе запроса, бюджет времени и подтверждённых билетов.
Неизвестный или повторный ID возвращает ошибку. Недостижимый переход,
закрытое место или превышение бюджета возвращают `ErrInfeasible`.

`Optimize` сначала пересчитывает исходный маршрут, не доверяя его старым
показателям. Затем проверяет развороты участков (2-opt для незамкнутого пути)
и обмены двух остановок (swap). Для каждой перестановки пересчитывается весь
маршрут: матрица направленная, обратные переходы могут отличаться или отсутствовать.
После каждого прохода выбирается лучший допустимый вариант, который строго
уменьшает время ходьбы. Равные варианты сохраняют первый найденный порядок.

Выполняется максимум 10 проходов (`MaxOptimizationPasses`); при отсутствии
улучшений поиск прекращается. Порядок перебора фиксирован, seed запроса
сохраняется. Состав мест и стоимость не меняются, исходные структуры не
изменяются, возврат к старту не добавляется. Свободное время не заполняется
новыми местами. При некорректном исходном маршруте или данных матрицы
возвращается ошибка; недопустимые альтернативные порядки пропускаются.

CLI включает оптимизацию по умолчанию и выводит ходьбу до и после неё.
Тесты в `optimize_test.go` проверяют независимые контрольные примеры для
2-opt и swap, направленную матрицу, недостижимые обратные переходы,
закрытый короткий маршрут, пересчёт времени и стоимости, одинаковые
результаты при повторном запуске, пустой маршрут и одну остановку.

Локально прошли полный набор тестов с PostgreSQL и `-race`, `go vet`, сборка
всех команд, форматирование и проверка diff. Существующий CI запускает новые
тесты автоматически в jobs планировщика и backend при следующем push.

Сквозная проверка на реальных PostgreSQL и Valhalla:
`--budget 180 --categories museums,architecture --start-time 2026-10-20T10:00 --ticket-budget 15 --seed 42`.
Для тех же 6 мест ходьба сократилась с 59,07 до 53,13 минуты (экономия
5,93 минуты), расстояние — до 4,41 км; осмотр остался 105 минут,
общее время составило 158,13 минуты, подтверждённая стоимость — 0 BYN.
Часы работы этих шести мест по-прежнему не подтверждены.

## Этап 21 октября: варианты маршрутов

`Request.Profile` задаёт предпочтение, не изменяя жёсткие ограничения:

| Профиль | Эффективность выбора следующего места |
|---|---|
| best_match (по умолчанию) | value / (walk + visit) |
| more_places | 1 / (walk + visit) |
| less_walking | value / (4 × walk + visit) |
| budget | value / ((walk + visit) × (1 + cost_BYN + unknown_price_penalty)) |

Для неизвестной цены в профиле budget применяется штраф 2, чтобы неизвестная
цена не выглядела предпочтительнее подтверждённой бесплатной. Правило бюджета
билетов остаётся прежним: ограничивается подтверждённая сумма.

`PlanVariants` строит шесть кандидатов: четыре профиля и два дополнительных
best_match с воспроизводимым возмущением эффективности в диапазоне 0,9–1,1.
Все используют одну матрицу; дополнительные кандидаты не вызывают Mapbox.
Каждый оптимизируется через 2-opt/swap, если оптимизация включена.

Все кандидаты ранжируются по общей настраиваемой оценке Score; стабильная
сортировка сохраняет порядок при равенстве. Пустые маршруты удаляются, похожие наборы мест отбрасываются
по коэффициенту Жаккара: пересечение / объединение >80%. Одинаковые места
в другом порядке не создают новый вариант. Возвращается от 0 до 3 вариантов;
три варианта не гарантируются, если допустимых разных маршрутов меньше.

CLI по умолчанию использует `--variants=true --optimize=true --geometry=true`.
`--variants=false --profile=best_match` возвращает один маршрут указанного
профиля. Итоговый Directions получает точки в выбранном порядке. Его переходы
подставляются вместо оценок Matrix, затем заново проверяются время, расписание
и билеты. Нарушающий ограничения вариант пропускается с предупреждением.
Темп применяется один раз. `--geometry=false` оставляет оценки Matrix.

Метки с порогом 10% добавлены на этапе 22 октября; объяснения добавлены на этапе 23 октября.
Подробности клиента и запуска: [Mapbox](mapbox.md).

## Этап 22 октября: оценка и метки

Общая оценка: `InterestValue − α × walk_km − β × cost_BYN − γ × unverified_count`.
`InterestValue` — сумма ценностей выбранных мест; неподтверждённое место
штрафуется один раз, даже если неизвестны и часы, и цена. По умолчанию
α=0,5; β=0,1; γ=0,5. `NewWithWeights` принимает любые конечные неотрицательные
коэффициенты, включая ноль. CLI загружает их через `PLANNER_WALK_PENALTY`,
`PLANNER_COST_PENALTY`, `PLANNER_UNVERIFIED_PENALTY`.
Greedy и пересчёт используют одну формулу; оптимизация обновляет оценку.

`AssignLabels` сравнивает все показанные итоговые варианты:

| Метка | Критерий |
|---|---|
| Лучший по интересам | Максимальный InterestValue |
| Больше мест | Максимальное число остановок |
| Меньше ходьбы | Минимальное расстояние WalkKM |
| Самый бюджетный | Минимальная стоимость; цены всех сравниваемых маршрутов известны |

Для каждой метки нужен единственный лучший результат и преимущество хотя бы
10% относительно каждого другого варианта. Для максимума: `best ≥ rival × 1,1`;
для минимума: `best ≤ rival × 0,9`; равенство показателей никогда не даёт метку.
Один маршрут может получить несколько меток. При единственном варианте меток
нет. Сравнивается числовой результат, а не название профиля генерации.

CLI сначала уточняет все пути через Directions, исключает нарушающие
ограничения варианты, затем заново присваивает метки между оставшимися.
Неизвестные цены запрещают бюджетную метку для всей группы сравнений.

Тесты проверяют самостоятельный расчёт оценки, нулевые/некорректные веса,
пересчёт после изменения порядка, точную границу 10%, меньшие различия,
нулевую стоимость, равенство, сравнение с каждым соперником и неизвестные цены.
Реальная проверка Mapbox выполнена: один допустимый вариант на 158 минут
при лимите 180 и подтверждённой стоимости 0 BYN; без сравнительных меток.

## Этап 23 октября: объяснения и сравнения

`Explain(route)` формирует сводку из итоговых остановок и показателей:
число мест, время, километры, состав по категориям, билеты и подтверждённость
расписания. Пример:

> 6 мест, до 3 ч 10 мин, 4,2 км пешком. По категориям: 3 памятника, 2 музея, 1 парк. Билеты: 18,50 BYN. По расписанию все места открыты на время осмотра.

Время округляется вверх до минуты, расстояние — до десятых километра,
цены выводятся точно в копейках BYN. Это форматирование не влияет на
проверку бюджетов. Категории сортируются для воспроизводимости; при
пересечении категорий сводка сообщает, что они могут пересекаться.

Неизвестные сведения считаются по флагам остановок: если цена неизвестна,
выводится подтверждённая сумма и предупреждение, без утверждения о бесплатных
билетах. При неизвестных часах не говорится, что все места открыты.
Для пустого маршрута используется отдельный текст.

`DiffRoutes(before, after)` возвращает подписанные изменения
`after − before` по минутам, километрам и копейкам, а также добавленные
и убранные ID. Для перестановки того же набора мест добавлений/удалений нет.
Порядок ID соответствует порядку остановок в соответствующем маршруте.
`ExplainDiff(diff, names)` выводит человеческий текст с названиями мест;
при отсутствии названия остаётся ID. Малые изменения не округляются до
нулевого сообщения. При неизвестных ценах сравнивается только подтверждённая сумма.

CLI формирует сводки после уточнения Directions и проверок ограничений.
Каждый следующий вариант сравнивается с первым показанным вариантом.
Функции сравнения пригодны и для будущего пересчёта маршрута.

Тесты проверяют сводку с независимо заданными показателями, склонения,
пересекающиеся категории, неизвестные часы/цены, пустой маршрут, знаки
изменений, добавления/удаления, перестановки, малые изменения и воспроизводимость.
Полный CLI проверен с реальным каталогом PostgreSQL и локальной заглушкой
Mapbox без расхода внешней квоты. Новые тесты автоматически входят в текущий CI.


## Приёмочные сценарии и benchmark

Этап 25 октября добавляет 10 фиксированных запросов на снимке 60 мест,
независимый аудит и регрессионный эталон. Алгоритмические тесты работают
без БД и сети; benchmark отдельно измеряет время и выделения памяти.
`cmd/planner-bench` выводит отчёт, а флаг `-mapbox` явно включает сетевую
проверку Matrix/Directions. Подробности, результаты и оставшаяся оценка
маршрутов людьми — в [отчёте этапа](day-25.md).
