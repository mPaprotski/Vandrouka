# 24 октября — приватные фотографии посещений

Реализовано досрочно 20 октября 2026 года. Backend умеет принимать, читать и удалять приватное фото; MinIO поднят отдельно для «Вандроўкі». Камера и мобильная отправка — день 26, подтверждение посещения/XP — день 25. Незавершённый день 22 (мобильный вход, SecureStore, refresh/logout) не объявляется выполненным.

## API

| Метод | Путь | Доступ и результат |
|---|---|---|
| POST | `/v1/visits/photo-upload` | Bearer, multipart с одним `place_id` и одним `file`; 201 с метаданными ready |
| GET | `/v1/visits/photos/{photo_id}` | Только владелец; JPEG/PNG без публичной ссылки |
| DELETE | `/v1/visits/photos/{photo_id}` | Только владелец; повтор идемпотентен; 204 после удаления объекта |

Владельца определяет серверная сессия, поле `user_id` не принимается. Для чужого, неизвестного, некорректного UUID и удалённого фото чтение даёт одинаковый 404. Чужое удаление также даёт 404. POST принимает только активное существующее место. Оригинальное имя файла не используется в ключе и не логируется.

Лимиты: **10 MiB** входного и обработанного файла, **20 000 000 пикселей**, **8192 пикселя по каждой стороне**. Сначала проверяются сигнатура и геометрия JPEG/PNG, затем файл полностью декодируется. MIME части multipart должен соответствовать реальному формату. Применяется EXIF-ориентация, JPEG кодируется с quality=85, PNG — стандартным encoder; EXIF/GPS, комментарии, текстовые PNG-чанки и остальные исходные метаданные не переносятся. Другие форматы не передаются их декодерам.

Одновременно выполняются не более двух операций с фото на процесс; upload ограничен шестью попытками в минуту на владельца, память ограничителя — 4096 владельцами. 429 содержит Retry-After. Общий таймаут media — 45 секунд, существующий сетевой ReadTimeout сервера — 10 секунд. Отсутствие или недоступность хранилища даёт 503 `media_unavailable`; каталог/auth продолжают работать.

На всех media-ответах, включая ошибки и таймауты, `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`. Перед отдачей байтов проверяются сохранённые размер и SHA-256 объекта. Клиент не получает owner ID, object_key, checksum и постоянный публичный URL. Запросы логируются по шаблону endpoint, без токена, UUID фото, имени файла, тела и GPS.

## Сохранение и восстановление после ошибок

1. Проверить и перекодировать изображение в пределах лимитов.
2. Убедиться в доступности отдельного приватного бакета; создать строку `uploading` с lease 15 минут. Ключ — случайный UUID под префиксом `visit-photos/`, без email/координат/имени пользователя.
3. Заблокировать строку фото в транзакции, выполнить PUT, сохранить фактические MIME/размер/геометрию/SHA-256 и перевести в `ready`. При конкуренции очистка пропускает заблокированную загрузку.
4. При ошибке/отмене закрыть транзакцию и отдельным коротким контекстом пометить фото как недоступное. Если процесс завершился до этого шага, оставшаяся uploading-строка будет найдена по lease.

Файловое хранилище и PostgreSQL не имеют общей транзакции. Ошибки PUT/commit могут оставить объект, поэтому добавлена миграция `000014_media_deletions.sql` — долговечная очередь удаления с повторами. Триггеры ставят ключ в очередь при soft delete и при физическом удалении метаданных, включая каскад удаления владельца. Очередь не имеет FK на пользователя и переживает такой каскад. Это техническая гарантия очистки; пользовательский endpoint удаления аккаунта пока отсутствует.

DELETE сначала коммитит tombstone и очередь, затем удаляет объект. Если S3 недоступно, возвращается 503, но новые GET уже получают 404. Повторный DELETE или worker завершит очистку. Удаление фото не меняет visit, XP или уникальность первой награды — утверждённое пользователем правило сохранено.

Worker запускается вместе с API при настроенном S3: сразу и раз в минуту, с бюджетом 30 секунд на цикл. За цикл до 25 устаревших метаданных и 25 jobs. Используются `FOR UPDATE SKIP LOCKED`, поэтому активный upload/confirm не очищается конкурентно. Неудачные удаления сохраняются с attempts и повтором через минуту.

Очищаются: истёкшие uploading (15 минут), failed, готовые фото старше 24 часов, не связанные с подтверждённым visit, и явно удалённые фото. Фото подтверждённых посещений не удаляются по TTL. После сбоя PUT удаление отложено до истечения lease, чтобы дать завершиться неоднозначному внешнему запросу. Строки метаданных остаются tombstone; сохранённый ключ позволяет повторить физическое удаление. Политика долгосрочной очистки tombstone и отдельных аккаунтов — отдельная задача до релиза.

## Локальное хранилище

Compose содержит отдельный `minio`, том `vandrouka_media_data`, внутренний S3 endpoint `http://minio:9000`. Хостовые порты привязаны только к loopback: `127.0.0.1:29000` (S3) и `127.0.0.1:29001` (консоль). Телефон получает фото через backend, а не через MinIO.

Настройки в игнорируемом `backend/.env`:

```dotenv
MEDIA_S3_ENDPOINT=http://127.0.0.1:29000
MEDIA_S3_BUCKET=vandrouka-visit-photos
MEDIA_S3_ACCESS_KEY=vandrouka-local
MEDIA_S3_SECRET_KEY=<случайный секрет не короче 16 символов>
```

Для текущего рабочего окружения секрет уже сгенерирован локально; в Git его нет. Compose заменяет endpoint на адрес контейнера. Команды из корня:

```bash
docker compose --env-file backend/.env up -d postgres minio
make migrate-up
docker compose --env-file backend/.env up -d --build api
```

Для свежего клона сначала скопировать `backend/.env.example` в `backend/.env` без перезаписи своего файла и заменить placeholder секрета. `make up/down` также читают этот env-файл. Без настроенного endpoint обычный `go run` сохраняет каталог/auth, а media-операции возвращают 503.

Бакет создаётся приватным. При инициализации клиент отказывается использовать бакет с существующей bucket policy вместо её молчаливой перезаписи; политика не меняется при обычных запросах. Доступы S3 никогда не добавляются в `mobile/.env.local`. Для внешнего развёртывания нужны HTTPS и отдельные права на бакет; текущий root-доступ относится только к отдельному локальному MinIO проекта.

Локально использован уже имеющийся образ `minio/minio:RELEASE.2025-09-07T16-13-09Z`, выбранный через `MINIO_IMAGE`. Community-сервер MinIO архивирован, а официальное распространение перешло к исходникам: [состояние upstream](https://github.com/minio/minio). Поэтому получение этого исторического образа на новом хосте не гарантируется; перед демо-развёртыванием нужно закрепить доступный образ/сборку либо подключить другое приватное S3-совместимое хранилище. Адаптер использует [официальный MinIO Go SDK](https://github.com/minio/minio-go/blob/v7.1.0/docs/API.md).

Том `media_data` нужно резервировать вместе с PostgreSQL. Обычный compose down сохраняет его; down -v удаляет данные и не является штатным способом перезапуска.

## Проверки

- Автономно: JPEG/PNG, EXIF-ориентация, удаление метаданных, неподдерживаемый/повреждённый формат, MIME mismatch, лимиты байтов/сторон/пикселей.
- HTTP: два владельца, отсутствие auth, приватные заголовки, некорректный multipart/дубли полей/подстановка user_id, read/delete, 429, таймаут и недоступность хранилища без утечки внутренних данных.
- PostgreSQL + memory object store: ready после PUT, чужой owner не достигает object store, checksum, сохранение XP, durable delete/retry/backoff, неоднозначный неудачный PUT, истёкший upload, TTL неподтверждённых фото, сохранение подтверждённых фото и гонка активного upload с worker.
- Настоящий локальный MinIO: отдельный временный бакет, PUT/GET/DELETE, запрет анонимного чтения и листинга, отказ от public bucket policy. Тестовый бакет удаляется.
- Миграция 14 up/down/up на отдельной тестовой БД. Основная БД получает только up, без очистки каталога.
- Полный Go `-race`, `go vet`, build, форматирование, OpenAPI и Docker build/config прошли.
- Сквозная проверка HTTP → PostgreSQL → настоящий MinIO прошла двумя временными аккаунтами. Проверены схема ответа, удаление метаданных, чужое фото, MIME mismatch, запрет анонимного чтения, сохранность объекта после перезапуска MinIO и 503/очередь при его остановке. После восстановления DELETE завершился и стал идемпотентным. Тестовые аккаунты удалены, MinIO оставлен запущенным. Каталог сохранил 60 мест и пять карточек подборки.

Обычные тесты не требуют MinIO: S3-интеграция включается через `TEST_MEDIA_S3_ENDPOINT`, `TEST_MEDIA_S3_ACCESS_KEY`, `TEST_MEDIA_S3_SECRET_KEY`. PostgreSQL требует отдельную `TEST_DATABASE_DSN`. CI запускает PostgreSQL/HTTP/изображения; настоящий MinIO проверен локально, не выдаётся за уже выполненный GitHub CI.

Mapbox и Android-эмулятор для этого этапа не используются. Телефонный сценарий загрузки ещё не проверен — мобильной камеры/отправки пока нет.
